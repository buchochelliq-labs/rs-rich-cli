# 0.0.18 cohort: intuiTUIve grows up

**Prepared; publication follows the merge of this release's last PR.** See
[Publication](#publication).

0.0.18 is the third release of
[intuiTUIve](../guide/intuituive/index.md), the TUI framework, and it is
the one where an app stops being only a terminal program:

- **Keys as they were pressed.** The kitty keyboard protocol in
  rs-rich-interact: Ctrl+I is not Tab, Shift+Enter is not Enter, and a key
  release can be read, on terminals that have the protocol. Terminals
  without it behave exactly as before.
- **More backends.** termion and termwiz beside crossterm, chosen with a
  feature, with the same keys, mouse, paste, suspend and restore.
- **Synchronized output.** Each frame is one synchronized update (DEC mode
  2026) on a terminal that answers the query for it, so a large redraw
  never shows half drawn; `RICH_SYNC_OUTPUT` forces it on or off.
- **Stylesheets.** A CSS subset for an app's look and layout: selectors by
  node kind, name and class, `:focus`, `:hover`, `:selected` and
  `:disabled`, colours, borders, padding, sizes and docking, read from a
  file and reloaded as it changes. Code wins over the sheet where both set
  something.
- **The widget gaps.** Horizontal scrolling, sortable and resizable table
  columns with a cell cursor, a virtual lazy tree, tooltips, drag and drop,
  and hover styles.
- **Accessibility.** Every node has a role, an accessible name and states
  (checked, expanded, selected, busy, disabled); an app can announce, mark
  nodes hidden from assistive technology, and run in an accessible mode
  that parks the cursor on the focus for a screen reader, or a linear mode
  that writes the accessibility tree as lines of text in reading order.
- **In a browser.** rs-rich-web (new) serves an app to a browser tab over a
  WebSocket, drawn by xterm.js or by a DOM renderer that carries the
  accessibility tree as ARIA; it also serves any terminal program on a
  PTY. `rich serve -- htop` does that from the CLI, behind its
  off-by-default `serve` feature. Localhost, a token in the URL, an Origin
  check and a session cap by default.
- **Embedding.** rs-rich-embed (new) puts a terminal pane (a shell or any
  program on a PTY) and a web view (Chrome over DevTools, Browsh, or a text
  browser) inside an app, each over a backend trait that can be swapped.

A default build of `rs-rich` is unchanged, still 0.0.9, and still renders
exactly like upstream `rich` 15.0.0.

## Migration

The 0.0.x crates take breaking changes. In rs-rich-interact:

- `Key` has a private field, so it is built with `Key::new`, `Key::with`,
  `Key::ctrl`, `Key::char` or `Key::parse`, not a struct literal.
- `Event` has a new variant: a `match` on it needs a `_` arm.
- `SessionOptions` has new fields: build it with
  `..SessionOptions::default()`.

## Publication

`RELEASES.toml` lists every package's version in publication order.
`rs-rich-data` 0.0.2 goes first, on its own: its tag already exists (on the
0.0.17 commit), and its first run stopped at the token exchange because the
crate had no Trusted Publishing entry. Add the entry (crate → Settings →
Trusted Publishing; see
[Registry authentication](../BRANCHING.md#registry-authentication-trusted-publishing)),
then re-run that tag's release (`release.yml`, "Re-run failed jobs", or a
manual dispatch of `rs-rich-data-v0.0.2`). `rs-rich-cli` 0.0.17 then need
not be published: 0.0.18 carries everything it had.

Then tag the rest on the merged commit on `main`, crates only, since the
Python package is held back:

```bash
python3 scripts/release_cohort.py status                              # what is published, tagged, or due
python3 scripts/release_cohort.py tag --registry crates.io --dry-run  # what it would tag
python3 scripts/release_cohort.py tag --registry crates.io            # tag and wait, one at a time
```

`tag` skips the packages already on crates.io and pushes one annotated tag
at a time, waiting for each version to appear before the next:

1. `rs-rich-record-v0.0.6`;
2. `rs-rich-interact-v0.0.6`;
3. `rs-rich-ratatui-v0.0.3`;
4. `rs-rich-intuituive-v0.0.3`;
5. `rs-rich-embed-v0.0.1`;
6. `rs-rich-web-v0.0.1`;
7. `rs-rich-cli-v0.0.18`.

`rs-rich-embed` and `rs-rich-web` are new crates: their first versions
upload with the `crates-io` environment's `CARGO_REGISTRY_TOKEN` secret, so
it must be set, and each needs its Trusted Publishing entry added right
after, before its next version.
