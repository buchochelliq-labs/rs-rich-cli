# Plan to 1.0.0

**Status:** proposed on 2026-10-11, after the 0.0.18 cohort and `rs-rich`
0.0.6 on PyPI were published. The maintainer decided all eight
[decisions](#decisions-for-the-maintainer) on 2026-10-11, including the
package split below and a plugin marketplace as part of 1.0. Tracked in
[#730](https://github.com/buchochelliq-labs/rs-rich-cli/issues/730).

**Goal:** 1.0.0 is a promise, not a feature set. It tells someone choosing
this project that the crates they depend on will not break under them, that
the core renders what Python `rich` renders, and that there is a written
policy for what can and cannot change. Features keep landing after 1.0; what
changes is that breaking them costs a major version.

## Where we are

Measured on `main` at `3cd1bce` (2026-10-11):

- **18 packages, all at 0.0.x:** 17 crates on crates.io and the Python
  package on PyPI, about 300,000 lines of Rust. Under Cargo's rules every
  0.0.x release is a breaking release, and 16 CHANGELOG lines mention a
  breaking change. The 0.0.18 migration notes (`Key` gaining a private field,
  `Event` gaining a variant, `SessionOptions` gaining fields) are typical:
  each would have been avoidable with `#[non_exhaustive]` and constructors.
- **Core parity:** `rs-rich` 0.0.9 mirrors `rich` 15.0.0, which is still
  upstream's latest release, and `rich-cli` 1.8.1, also still the latest.
  [PORTING](../PORTING.md) has 19 rows complete, 41 partial and 5 not
  started (`scope.py`; `repr.py`/`_inspect.py`; the Windows console modules;
  `jupyter.py` and friends; internal helpers). The `rich-rst` pin was 1.3.2,
  with upstream at 2.2.0; it moved to 2.2.0 in 0.0.23.
- **Divergences:** [DIVERGENCES](../DIVERGENCES.md) lists 30 open
  entries. Some are deliberate and permanent (syntect instead of Pygments,
  no random hyperlink `id=`, Python-object modules reimagined); others are
  gaps that read like bugs (§7 a table padding edge, §12 `Screen`'s trailing
  separator, §28 `AnsiDecoder` splitting like rich 12, §29 renderables that
  cannot end without a newline, §32 `Columns(width=0)`, §33 a GFM delimiter
  row in a list).
- **Confidence tooling that exists:** byte-for-byte golden fixtures, a
  nightly 20,000-case differential fuzzer for markup, styles and box
  renderables, three-audit release tests, tapes checked against their
  recordings, MSRV and feature-matrix CI on Linux, macOS and Windows.
- **Stability tooling that does not exist:** no `cargo-semver-checks`, no
  public-API snapshots, no `missing_docs` lint, no written policy on whether
  a change in rendered bytes is a breaking change, and only 26
  `#[non_exhaustive]` markers across core, ext and the plugin API.
- **Public dependencies:** core's default features expose `syntect` and
  `pulldown-cmark`; `rs-rich-art` re-exports `image`; `rs-rich-ratatui`
  re-exports `ratatui_core`; `rs-rich-interact` builds on `crossterm` and
  `termwiz`. A 1.0 crate that exposes a 0.x dependency's types inherits that
  dependency's breaking changes.
- **Issues:** 213 open. Many were delivered and never closed (most of the
  0.0.16 data milestone, the intuiTUIve framework track #160–#170, #678
  termwiz, #240 DOT, #244 JSON Schema, #247 ER diagrams). Milestones 7 and 8
  are named "0.0.17" and "0.0.18" but describe work those releases did not
  ship. Milestone 13, "1.0.0 – Stable ecosystem architecture", holds five
  issues: #12 Windows legacy console, #232 the plugin ecosystem, #380
  splitting the monorepo, #463 a marketplace browser, #670 browser
  recording.
- **Python:** abi3 wheels for CPython 3.9 and later. 3.9 reached end of life
  in October 2025.

## What 1.0.0 covers

**Decided (2026-10-11):** a *stable set* of packages goes to 1.0.0
together; every other package moves to 0.1.0 and graduates on its own
evidence later.

| Package | At 1.0 | Why |
|---|---|---|
| `rs-rich` | **1.0.0** | The faithful core; the reason the project exists |
| `rs-rich-plugin-api` | **1.0.0** | Third-party plugins need a contract that holds; its native/WASM ABI already has `ABI_MAJOR` |
| `rs-rich-macros` | **1.0.0** | Small, and `rs-rich-ext` exposes it |
| `rs-rich-ext` | **1.0.0** | Most users' second dependency; depends only on the three above |
| `rs-rich-cli` | **1.0.0** | Its contract is the command line: flags, exit codes and the JSON report envelope, not a Rust API, and `rich plugin`. Commands newer than one release are listed as experimental and outside the promise |
| `rs-rich` (PyPI) | **1.0.0** | The Python surface of the stable set; `rs_rich.tui` and other wrappers of 0.x crates stay provisional |
| `rs-rich-marketplace` (new) | **1.0.0** | The marketplace client: the listing format, verification and the install lockfile, which `rich plugin` and third-party tools share |
| `rs-rich-art`, `-diagram`, `-mermaid`, `-lumis`, `-data`, `-micro`, `-record` | 0.1.0 | Mature enough to stop breaking every release, not yet reviewed for 1.0 |
| `rs-rich-interact`, `-intuituive`, `-ratatui`, `-web`, `-embed` | 0.1.0 | Young (web and embed are 0.0.1) and still taking breaking changes each release |

The libraries in the stable set (core, plugin API, macros, ext and the
marketplace client) depend on no 0.x crate of ours, so their promise does
not depend on theirs. The CLI and the Python package are different: the CLI
depends on `rs-rich-data` and `rs-rich-diagram` unconditionally and enables
more 0.x crates by default, and the Python package bundles nearly all of
them. Their promise is therefore drawn around what they expose, not around
what they link:

- Every CLI command and every Python module is classed in stage 3 as
  *stable* or *experimental*, by the crate behind it. A stable one is
  covered whatever crate implements it; an experimental one is marked in
  `--help` and the Python docs and is outside the promise.
- A 0.x crate's breaking release that reaches a stable command or module
  is absorbed inside the CLI or binding without changing what users see;
  if it cannot be, the change waits for the next CLI or Python major.
- The CLI and the Python package pin each 0.x dependency to one minor
  (`0.1`), so Cargo never pulls a breaking release into a 1.0 build.

Moving the rest from 0.0.x to 0.1.0 matters on its
own: from 0.1.0, Cargo treats 0.1.1 as compatible with 0.1.0, so those
crates can ship fixes without forcing every dependent to bump.

## The path

Six stages, each a release or a short run of releases; stage 2 runs two
tracks side by side. The issue backlog
(about 180 feature issues across data, observability, reports, art, diagrams
and interactive components) is **not** a 1.0 prerequisite: it continues in
the 0.x crates and in `rs-rich-ext` minor releases throughout, except during
the release-candidate freeze.

  against the CHANGELOG; move any undelivered remainder into a new issue.
- Rename milestones by theme instead of by version ("Observability &

### Stage 2 — parity complete, and the marketplace (0.0.20 to 0.0.22)

Both tracks are planned in [0.0.22](0.0.22.md): 0.0.20 became the demo
loop's release and 0.0.21 a widgets and docs release, which laid the
marketplace's listing format.

#### Track A: parity

The core's promise at 1.0 is "renders what `rich` renders". Make it true,
or write down exactly where it is not.

- **Every partial row in PORTING** gets a short list of what is missing,
  then is ported or recorded as a divergence. 41 rows, grouped into four
  workstreams: rendering core (`segment`, `text`, `console`, `style`,
  `color`, `markup`, `measure`, `ansi`, `highlighter`), widgets and layout
  (`panel`, `padding`, `align`, `table`, `layout`, `bar`, `screen`, …),
  live display (`live`, `progress`, `status`, `spinner`, including §17's
  deferred alternate screen and redirect), and documents (`markdown`,
  `syntax`, `json`, `pretty`, `traceback`, `prompt`).
- **Port `scope.py`** (`render_scope`), the one small module not started.
- **Each open divergence gets a verdict:** fixed, or permanent with its
  reason. The bug-like ones listed above are fixed unless a fix is
  impossible.
- **Widen the differential fuzzer** to Markdown, Tree, Columns, Progress
  frames, Pretty and JSON, so parity is measured rather than sampled.
- **Sync any upstream release** that appeared meanwhile, and the `rich-rst`
  pin to 2.x.
- **Windows legacy console (#12):** settle per the decision below.

#### Track B: the plugin marketplace (#232, #463)

Plugins already work three ways (PLUGINS.md): as a Cargo dependency, as a
native library loaded from a path, and as a WASM module loaded from a path,
behind off-by-default features, with `--plugin` and a user-only `plugins`
list. What is missing is a way to *find, trust, install and update* one.
Micro asset packs (#582) have the same gap, so they share the design.

- **The listings:** a Git repository, `buchochelliq-labs/rs-rich-marketplace`
  (named on 2026-10-11), with one file per package: id, kind (Cargo crate, WASM plugin, micro pack,
  theme), versions, SHA-256 of each artifact, source repository,
  capabilities, declared permissions, and the plugin API and ABI versions it
  needs. The format has a `schema_version` and is part of the 1.0 promise.
  Crates stay on crates.io and WASM modules on GitHub releases; the marketplace
  stores where they are and what they hash to, not the files.
- **Trust:** the listings are signed (minisign key held by the maintainer), every
  download is checked against its hash, and entries carry a tier:
  *official* (this repository's plugins), *reviewed* and *community*. A
  package can be yanked. Only WASM plugins and asset packs are installable
  from the marketplace; a native library still has to be named by path, because it
  runs with the user's full rights.
- **`rs-rich-marketplace` (new crate):** reads and verifies the listings, resolves a
  version against the running host's plugin API and ABI, downloads and checks
  artifacts, and keeps a lockfile of what is installed. No terminal code: the
  CLI and other tools build on it.
- **`rich plugin`:** `search`, `info`, `install`, `update`, `remove`, `list`,
  `enable`, `disable` and `verify`; an installed plugin is loaded on the
  next run without `--plugin`. `install` shows the permissions and tier and
  asks before it writes anything; `--yes` for scripts.
- **`rich plugin browse`** (#463): the same operations in an interactive
  browser built on `rs-rich-interact`'s selector and preview, with provenance
  shown for each entry.
- **Publishing:** `rich plugin publish` checks a package locally and writes
  the listing; it is submitted as a pull request to the marketplace repository, whose CI
  builds or downloads the artifact, checks the hash and the ABI, and runs the
  plugin against the current host.
- **Compatibility tests:** every official plugin (Mermaid, DOT, lumis) and a
  fixture WASM plugin are installed from a test marketplace in CI against each host
  version, so a host change that breaks installed plugins fails a PR.
- **Maintainer actions:** the `rs-rich-marketplace` repository exists (2026-10-11).
  The signing keys are a main and a backup minisign pair made by the
  maintainer: the main key a secret of a protected environment in the
  marketplace repository, so CI signs each index, and the backup kept
  offline for rotations (decided 2026-10-21,
  [0.0.22 plan](0.0.22.md#decisions)); only their public halves enter the
  repositories.

### Stage 3 — API review and stability tooling (0.1.0)

This is the release that makes 1.0 possible. Every package moves to 0.1.0;
the stable set's public API is reviewed item by item.

- **Snapshots of the public API** per crate (`cargo public-api`), checked
  into the repository and diffed in CI, so every API change is visible in
  review.
- **`cargo-semver-checks`** in CI against each crate's last published
  version, and in `scripts/release.py plan`, which refuses a version bump
  smaller than the change.
- **Brought forward to 0.0.23, and done there** (the maintainer's call on
  2026-10-26): the snapshots, `cargo-semver-checks` in CI and in the plan,
  and the Python stubs below. See the
  [0.0.23 plan](0.0.23.md#15-api-checks-python-stubs-and-two-fixes-all-crates-pypi).
  - **Snapshots:** `api/<crate>.txt`, `scripts/public_api.py`, CI's
    `public API and SemVer` job.
  - **SemVer:** for 0.0.x, where Cargo counts every bump as breaking, CI
    checks each crate as if its bump were a minor one and holds every
    breaking change to `api/semver-breaks.toml`.
  - **What stays for this stage:** the review itself, and the move to
    CPython 3.10 with the provisional modules marked.
- **The review itself**, against the Rust API guidelines: `#[non_exhaustive]`
  on every public enum and option struct that may grow, constructors or
  builders instead of public fields where a field may be added, sealed
  traits where only we implement them, error types that implement
  `std::error::Error` and can grow, `Send`/`Sync` stated and tested, names
  consistent across crates.
- **Public dependencies:** for each stable crate, list every foreign type in
  its API. Hide it behind our own type, or keep it only behind a feature
  documented as "follows `<dependency>`'s major version". `syntect` and
  `pulldown-cmark` in core are the main cases.
- **Features:** audit names and defaults; after 1.0, removing a feature or
  changing a default is breaking.
- **Documentation:** `missing_docs` set to deny on the stable set, an example
  on each main type, `doc_cfg` badges for feature-gated items on docs.rs.
- **The CLI and Python contracts:** freeze and document the exit-code
  classes and give the JSON report envelope a schema version; class every
  CLI command and Python module as stable or experimental by the crate
  behind it (see [What 1.0.0 covers](#what-100-covers)) and mark the
  experimental ones in `--help` and the Python docs.
- **Toolchain:** move to edition 2024 before the freeze (it can change
  behavior, so it belongs before the review, not after), and write down the
  MSRV policy (proposed: the latest stable minus six releases; raising it is
  a minor release).
- **Python:** complete `.pyi` stubs (done in 0.0.23, checked against the
  wheel by `stubtest` in CI), raise the minimum to CPython 3.10, and mark the
  provisional modules.
- **Core's own types, made cheap:** brought forward to 0.0.23 by the
  maintainer on 2026-10-25 ("make the strings lighter"), and done there.
  - **What changed:** `Segment.text` and `Color.name` are
    `rich::CompactString`s, with output byte-identical. See the
    [0.0.23 plan](0.0.23.md#7-lighter-strings-in-core-and-rs-rich-exts-fast-path-rich-ext-intuituive).
  - **What the review does:** check the result as part of the public API.

### Stage 4 — hardening (0.1.x)

- **Fuzzing:** `cargo-fuzz` targets, run in nightly CI, for every parser that
  takes outside input: markup, the ANSI decoder, Markdown, DOT, Mermaid,
  CSV/JSONL, stylesheets, the VT emulator, WebSocket frames and the plugin
  ABI's inputs.
- **A threat model** for the parts that run other code or serve a network:
  dylib and WASM plugins, the marketplace's listings, signatures and
  downloads, `rich serve`, the embedded web view.
- **A security review of the marketplace** before the release candidate,
  as its own audit, with the marketplace's signing key handling included.
- **Benchmarks with thresholds** enforced in CI (the open half of the
  [ROADMAP](../ROADMAP.md#benchmarks) item), so a slowdown fails a PR the
  way a parity break does.
- **The real-terminal and screen-reader passes** become a recorded checklist
  run on every stable-set release, not only when protocols change.
- **Dogfood outside this repository:** #564 proposes rs-rich as the shared
  CLI layer for other BuchochelliQ Labs tools. Building one of them on the
  0.1 API is the best test that the API is usable by someone who did not
  write it.

### Stage 5 — release candidates (1.0.0-rc.N)

- Tag `1.0.0-rc.1` for the stable set. The release tooling already handles
  prereleases.
- **Freeze:** no feature merges into the stable set until 1.0.0; fixes only,
  each with a regression test. The 0.x crates keep moving.
- At least two weeks between the last rc and 1.0.0, with the dogfood
  project on the rc.
- The full release test: three independent audits, `validate_release.py`,
  parity, tapes, the real-terminal and screen-reader checklist.
- Publish the stability policy and a 0.0.x → 1.0 migration guide.

### Stage 6 — 1.0.0

Publish the stable set and the Python package, then retarget the issue
backlog at post-1.0 minor releases.

## Exit criteria for 1.0.0

For each package in the stable set:

- [ ] Every PORTING row (core) is complete or has a DIVERGENCES entry
      marked permanent; no open divergence reads as a bug.
- [ ] The public API snapshot has been reviewed and is unchanged across the
      last release candidate.
- [ ] `cargo-semver-checks` and the API snapshot diff run in CI and the
      release tooling.
- [ ] Every public item is documented; `missing_docs` is denied.
- [ ] No foreign type in the public API outside a documented feature.
- [ ] Fuzz targets for its parsers have run in nightly CI for at least four
      weeks without an open finding.
- [ ] The stability policy, MSRV policy and migration guide are published.
- [ ] One project outside this repository builds on it.

For the marketplace:

- [ ] The marketplace is live, signed, and lists every official plugin and the
      built-in micro packs.
- [ ] A third-party WASM plugin has gone through `rich plugin publish`, the
      marketplace's CI and `rich plugin install` end to end.
- [ ] The compatibility tests run in CI for every official plugin.

## Decisions for the maintainer

Each is marked decided, with the date, or open with a recommendation.

1. **Which packages go to 1.0?** Decided (2026-10-11): the stable set above,
   with everything else at 0.1.0.
2. **Is a change in rendered output a breaking change?** Decided
   (2026-10-11): no, with exceptions. Bytes that move *towards* upstream `rich` are fixes and
   ship in minor or patch releases. What is covered: the Rust API, the CLI's
   flags, exit codes and JSON reports, and the export formats' structure.
   Otherwise every parity fix after 1.0 would need 2.0.
3. **Byte-parity as the north star after 1.0** (the ROADMAP's open
   question). Decided (2026-10-11): yes for *output*; no for *API shape*. §3 (byte
   offsets in `Text` spans where upstream counts code points) stays: it is
   the right Rust API and does not change what is rendered.
4. **Upstream's next major (`rich` 16).** Decided (2026-10-11): sync it
   like any release. Output changes follow decision 2; only an API change we cannot
   absorb compatibly makes `rs-rich` 2.0.
5. **Splitting the monorepo (#380).** Decided (2026-10-11): after 1.0, not as part of
   it. The issue's own preconditions (a proven plugin API, a marketplace
   underway, the workspace measurably slowing work) are not met, and moving
   repositories during an API freeze adds risk for no user benefit.
6. **The plugin marketplace (#232, #463).** Decided (2026-10-11): part of
   1.0, contract and marketplace both: the listings repository, `rs-rich-marketplace`,
   `rich plugin` and the browser (stage 2, track B).
7. **Windows legacy console (#12).** Decided (2026-10-11): declare it unsupported
   (Windows 10 and later only, as every supported Windows release is), close
   #12, and record it in DIVERGENCES. Implementing it needs `unsafe` in core
   for terminals almost nobody runs.
8. **A stop at 0.1.0.** Decided (2026-10-11): yes, as described in stage 3, so the
   API review and its tooling get a release of real use before the freeze.

## Sizing

No dates: in stage releases, 0.0.19, three releases for parity and the
marketplace, 0.1.0, one or two 0.1.x hardening releases, at least one
release candidate, then 1.0.0. That is eight or nine releases. At the recent pace of a cohort every few days to
a week, with three-audit release tests, it is a matter of weeks, not months.
The longest poles are stage 2's 41 partial rows, the marketplace, and
stage 3's API review; all three split into parallel workstreams.
