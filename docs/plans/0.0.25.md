# 0.0.25 plan: the two tracks' last release, and the release kit

**Status:** planned (2026-11-03). 0.0.24 was published on 2026-11-03,
and the 0.0.25 versions are open (see [Versions](#versions)).

Planned on 2026-11-03. 0.0.24 took almost all of
[the two tracks](1.0.0.md#before-010-the-apps-and-the-wider-stable-set-0024-to-0028)
(34 of the apps track's 36 issues, edition 2024, the signer's GitHub App,

It belongs to the stage before 0.1.0 in the [plan to 1.0.0](1.0.0.md).

**Target: about 7 November 2026.** The maintainer aims 1.0.0 at the
beginning of December (the 1.0.0 plan's decision 16), which puts 0.1.0
about 14 November and `1.0.0-rc.1` about 19 November. So 0.0.25 takes
what is ready in about four days; the rest moves on under decision 1
below.

## Workstreams

### 1. Release with release-kit (rs-rich-cli, release tooling)

- `release-kit.yml`: `name_from: rs-rich-cli`; every crate of
  `RELEASES.toml`, in its order, as a `crates.io` package; `rs-rich` on
  PyPI with `tag: "python-v{version}"` (the crate tag `rs-rich-v0.0.12`
  already exists) and a maturin artifact per target whose `test` installs
  the wheel and imports it.
- `python3 release.py install` from release-kit v1.7.0 puts the kit under
  `.github/release-kit/`; `release.yml` keeps this repository's own jobs
  (cargo-semver-checks, the playground) and calls ci.yml with
  `checkout_ref`.
- The record tags the old scripts wrote carry no registry; the kit's tag
  check needs one. `release.py check` runs against the existing tags before
  the switch, and a note in `docs/BRANCHING.md` says which tags predate it.
- `docs/BRANCHING.md` and the release skill describe the kit's commands
  (`tag`, `gate --verify-only`, `consume`).
- **The maintainer:** moves PyPI's trusted publisher to `release.yml` with
  the `pypi` environment.
- **Verified by** `release.py check` and `plan` in CI, a dry run of `tag`,
  and the kit's own tests; the first real use is 0.0.25's release.

**Done (wave 1, 2026-11-04).** What was found and decided:

- **The kit's schema fitted as its migration page shows.** `release-kit.yml`
  lists the 21 crates and the PyPI `rs-rich` in `RELEASES.toml`'s order;
  each package's `paths` is its `include` (plus `Cargo.lock` for the three
  binaries; the PyPI package's are its directory, the workspace manifest and
  the crates it builds from), for the kit's split check. The maturin
  artifact keeps pypi-release.yml's five targets and runners (macOS x86_64
  on `macos-15-intel`, not the kit's cross-compiled default, so its wheel is
  still tested); its `test` runs `crates/rich-py/tests/smoke.py` on every
  target, and on linux x86_64 also the compatibility suite against rich
  15.0.0 and the stub check, as pypi-release.yml's `test` job did.
- **`release.yml` is replaced, not kept beside the kit:** the kit's
  migration page prescribes it, and the 0.0.25 release is the kit's. It is
  the kit's template with the publish jobs this repository uses
  (`publish-crates`, `publish-pypi`), CI called with `checkout_ref`, and two
  jobs of its own: `semver` (`scripts/release.py plan --semver-checks` on the
  gate's crates; both publish jobs wait for it) and `publish-playground`.
- **The playground job is named `publish…`, the reverse of this plan's
  first wording.** The kit's rule (its workflow and recovery pages) is that
  every job that uploads anywhere is named `publish…`, since `tag` reads such
  a job's start as a possible upload and then never moves the run's tags;
  the old workflow's rule was the opposite. The job needs `publish-crates`
  to have succeeded, so its name changes no outcome either way.
- **`pypi-release.yml` no longer starts on `python-v…` tags,** which the
  kit pushes as records: it would publish the same version twice. It stays
  as a manual fallback (`workflow_dispatch` with a tag) until it retires.
- **The old tags need no config option.** The kit checks a tag's ownership
  only for a package's current, unpublished version, and refuses to resume a
  release whose commit has no `release-kit.yml`. All 200 tags (fetched
  2026-11-04) are annotated and name versions already published, so none is
  ever selected or moved; `tag --dry-run` against them (from a throwaway
  remote) tags the 22 packages of 0.0.25 and the release tag.
  `docs/BRANCHING.md`, "Tags from before release-kit", says which they are.
- **Rehearsal in CI:** `scripts/release_rehearsal.py` runs `check`,
  `vendored`, `plan` (every package) and `tag --dry-run` against a
  throwaway remote holding `HEAD` and origin's tags; `release-tests` runs it.
  The gate (`gate` and `gate --verify-only`) was also run by hand against a
  real `tag` pushed into a throwaway remote.
- **Not verified:** a real run (the first is 0.0.25's release), the wheel
  `test` on the runners, and `actionlint` (not available here).

### 3. The rest of Textual parity (rs-rich-intuituive, core)

- #812's remaining properties, each with a stylesheet test.
- `DataTable` row labels and renderable cells; option-list separators;
  carried highlighting state for `TextArea`.
- The audit's rows move to ✓ as each lands.
- **The fuzz finding of 2026-11-03** ([fuzzing](../design/fuzzing.md#known-findings)):
  921 bytes of `&` nesting selectors and `,` lists took the parser 12
  seconds and 1.4 GB. **Fixed on 2026-11-03,** ahead of the waves: each
  nested rule was read once per parent selector and each `&` replaced by
  the parent's text, so selectors grew exponentially. Nesting is now at
  most 32 deep and expansion bounded, with the input as a regression
  test ([fuzzing](../design/fuzzing.md#known-findings)). This comes first: it stops the four-week fuzz clock of
  the 1.0 exit criteria until it is fixed.

### 4. Named pipes on Windows (rs-rich-interact, rs-rich-cli, noctiluca)

## Order of work

The stylesheet fuzz fix goes to `main` on its own, ahead of the waves:
the four-week fuzz clock restarts with the first clean nightly run after
it merges, and 1.0.0's date rests on that clock.


- **Wave 0:** this plan; then 0.0.24's publication with the versions
  opened (workstream 6).
- **Wave 1**, in parallel worktrees, one integration pull request:
  workstreams 1 to 5.
- **The release pull request**, then the maintainer tags with release-kit:
  `python3 .github/release-kit/scripts/release.py tag`.

Every agent commits at milestones (WIP-marked), backs up to
`claude/next-priority-items-3c5p8e-wip-<name>`, and keeps
[the handoff note](../design/intuituive-status.md) current.
