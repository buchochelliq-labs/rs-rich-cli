# 0.0.19 plan: layout, editing, isolation, and docs you can see

**Status:** proposed on 2026-10-12, after the 0.0.18 cohort and `rs-rich`
0.0.6 on PyPI were published. It is stage 1 of the
[plan to 1.0.0](1.0.0.md). Its four framework items were decided with the
maintainer on 2026-10-08 (see the 0.0.18 plan's
[Not in this release](0.0.18.md#not-in-this-release)); the docs workstream
was asked for on 2026-10-12. The [decisions](#decisions) below were
answered on 2026-10-12. The tracker is
[#732](https://github.com/buchochelliq-labs/rs-rich-cli/issues/732).

**Goal:** close the gaps a comparison with other terminal frameworks found,
take the last known security edge out of rs-rich-embed, and make the docs
show what the code does on every page.

- **Flex alignment:** `align` and `justify`, and `wrap`, in layout and in
  the stylesheet, as Ink and iocraft have.
- **A text-area widget:** a multi-line editor with syntax highlighting,
  selection and undo, as Textual has.
- **One process per browser session** in rs-rich-web, as textual-serve
  isolates each session.
- **A `Surface` drawing handle in rs-rich-ext:** intuiTUIve's screen and
  damage-based painter moved down, with a small `surface.draw(|s| …)` API,
  so plain rich users get positioned rendering that repaints only what
  changed, as ratatui's `Frame` gives.
- **The Chrome web view's DevTools over a pipe**, not a port other local
  users can reach. Moved to 0.0.20 on 2026-10-13: see
  [workstream 5](#5-devtools-over-a-pipe-embed).
- **Docs with an example and a picture on every page**, and recordings of
  everything 0.0.18 added.

**What stays the same:** core. Nothing under `crates/rich/src` changes, and
every golden and the differential corpus stay byte-identical. The
intuiTUIve-against-ratatui benchmark gate keeps passing, now also with the
`Surface` underneath.

## Research behind this plan

- **The framework comparison** (2026-10-08) behind the 0.0.18 plan's list:
  Ink and iocraft lay out with flexbox alignment; Textual has a `TextArea`
  with highlighting; textual-serve runs a process per browser session;
  ratatui's `Frame` gives positioned, diffed drawing without a framework.
- **The code today** (`main` at `e48551e`):
  - `rich_intuituive::layout` solves sizes along one axis (fixed,
    percent, flex, auto, with min/max clamps, as CSS resolves flexible
    lengths) and places children from the start; there is no cross-axis
    alignment, no main-axis distribution and no wrapping.
    `sheet.rs` knows `size`, `padding`, `gap`, `grid-rows`, `display` and
    `dock`, none for alignment.
  - `rich_interact::TextArea` is a plain multi-line editor (`rich write`,
    #493): grapheme-aware editing and wrapping, no highlighting, selection
    or undo. intuiTUIve can host it as a text box.
  - `rs-rich-web` runs each browser session's app on a thread in the
    server's process (`http.rs`); `serve_command` already runs each
    session's program on its own PTY.
  - `rich_intuituive::screen` holds the cell `Screen` and the `Painter`
    that writes only damaged cells; `rich_ext::frame` already has `Frame`,
    its cell diff and graphics placement planning, which a `Surface` can
    build on.
  - `rs-rich-embed`'s Chrome engine starts Chrome with
    `--remote-debugging-port=0`, the known limit in the
    [0.0.18 notes](../releases/0.0.18.md#known-limits).
- **A docs audit** (2026-10-12) of every page under `docs/`:
  - the Python site's 40 pages have examples but not one picture of what
    they print;
  - these Rust guide pages have no screenshot at all: rs-rich-data (all
    three pages), ratatui interop, custom components in rs-rich-interact,
    sources, code highlighters and transforms in rs-rich-ext, intuiTUIve's
    web, embed and Python pages, getting started, tutorial step 6, and the
    overviews of the guide, the core guide, rs-rich-ext and micro assets;
    explorers in rs-rich-interact shows one of the explorers it describes;
  - two guide pages are procedures, not output, and stay without one: the
    screen-reader checklist and the CLI smoke test;
  - of 33 tapes, none shows a 0.0.18 feature: stylesheets, table sorting
    and resizing, the lazy tree, tooltips, drag-and-drop, accessible and
    linear mode, `rich serve` or the terminal pane.

## Workstreams

Each workstream lands as its own pull request, or a short stack, with an
entry under [Delivered](#delivered). Placement follows `AGENTS.md`: the
framework in rs-rich-intuituive, the drawing handle in rs-rich-ext, browser
serving in rs-rich-web, the web view in rs-rich-embed, Python in
`crates/rich-py`.

### 1. Flex alignment: intuituive

- **Cross axis:** `.align_items(Align::Start | Center | End | Stretch)` on a
  container and `.align_self(..)` on a child. `Stretch` is today's
  behaviour and stays the default.
- **Main axis:** `.justify(Justify::Start | Center | End | SpaceBetween |
  SpaceAround | SpaceEvenly)`, applied to what the flexible children leave;
  a container with a flexible child has nothing left, as in CSS.
- **Wrapping:** `.wrap()` on a row or column moves children that do not
  fit to a new line, each line solved as today; `align_content` places the
  lines.
- **In the stylesheet:** `align-items`, `align-self`, `justify-content`,
  `flex-wrap` and `align-content`, with CSS's names and values; code wins
  over the sheet, as for every other property. The inspector shows them.
- **Tests:** solver unit tests against the rectangles CSS flexbox gives for
  the same boxes, each alignment in rows and columns, wrapped and not, and
  with min/max clamps.

### 2. A text-area widget: intuituive, interact, ext

- `text_area(text: Signal<String>)` with `.language("rust")` for
  highlighting through the [code highlighters](../guide/ext/code-highlighters.md)
  (syntect by default, lumis when registered), `.line_numbers()`,
  `.soft_wrap(bool)` (horizontal scrolling when off), `.read_only()` and
  `.placeholder(..)`.
- **Editing:** grapheme-aware caret and editing shared with
  `rich_interact::TextArea` by moving its buffer into
  `rich_interact::edit::Buffer`, which both use; word moves (Ctrl+←/→),
  Home/End, PageUp/PageDown, indent and outdent with Tab and Shift+Tab.
- **Selection:** Shift with any move, the mouse (drag, double-click a word,
  triple-click a line), select all; copy, cut and paste through OSC 52 and
  bracketed paste.
- **Undo and redo** (Ctrl+Z, Ctrl+Y or Ctrl+Shift+Z), grouping typed runs.
- **Large text:** stored by line, only the lines in view highlighted and
  drawn, so a 100,000-line file scrolls without a stall (a benchmark).
- **Accessibility:** a multi-line text box role, the caret line announced
  in linear mode.
- **Python:** `rs_rich.tui.text_area`.

### 3. One process per browser session: web

- **`serve` runs each session in its own process.** The server re-executes
  its own binary with `RS_RICH_WEB_SESSION` set; the same `serve(addr, app)`
  call in that child runs the app over a framed pipe instead of binding a
  port, so an app needs no change. The parent keeps the WebSocket and
  forwards input, resize, paste and output frames.
- **Limits per session:** the process group is killed when the tab closes
  or the server stops (as `serve_command` does since 0.0.18), and an
  optional memory and CPU-time limit (`setrlimit` on Unix).
- **`Isolation::Threads`** keeps 0.0.18's behaviour for programs that
  cannot re-execute themselves (tests, embedded uses).
- **Python:** `rs_rich.tui.serve` re-executes the interpreter with the same
  script and arguments.
- **Tests:** a crash, a hang and a memory blow-up in one session leave
  the others and the server running.

### 4. A `Surface` drawing handle: ext, intuituive

- `rich_ext::surface::Surface` owns a cell buffer, the previous frame and a
  writer. `surface.draw(|s| { s.render(rect, &renderable); s.set_cursor(..) })`
  renders any rich renderable into a rectangle, then writes only the cells
  that changed (`rich_ext::frame`'s diff), in synchronized output where the
  terminal has it.
- Alternate screen or inline (a fixed number of rows below the prompt), a
  resize handled by redrawing everything once, and graphics placements
  carried over from frames.
- **intuiTUIve builds on it:** `rich_intuituive::screen::{Screen, Painter}`
  become re-exports of the ext types (names kept), so the benchmark gate
  measures the same code plain users get.
- **Python:** `rs_rich.ext.Surface`.
- **Docs:** a guide page, "Positioned drawing", with the ratatui comparison.

### 5. DevTools over a pipe: embed

- Chrome starts with `--remote-debugging-pipe`; the engine talks CDP over
  file descriptors 3 and 4 (NUL-separated JSON) and no port is opened. The
  descriptors are passed with the `command-fds` crate, so the crate keeps
  `unsafe_code = "deny"`.
- **Windows too** (decision 6): Chrome takes the pipe there as two
  inherited handles named by `--remote-debugging-io-pipes`, which `std`
  cannot mark inheritable. The pipe ships on all three platforms or on
  none: if Windows cannot pass the handles without `unsafe` in this
  workspace (through a maintained crate, as `command-fds` does on Unix),
  the whole workstream moves to 0.0.20 and the port stays everywhere,
  still documented as a known limit.
- **Tests:** no listening socket appears while a view is open, on Linux,
  macOS and Windows, and the existing CDP tests pass over the pipe.
- **Moved to 0.0.20 (2026-10-13).** Windows fails the test above. Chrome
  takes the pipe there either as `--remote-debugging-io-pipes=READ,WRITE`
  (two inheritable handle values in one switch) or as C runtime
  descriptors 3 and 4 (`STARTUPINFO.lpReserved2`). `std` can do neither,
  `os_pipe` and `filedescriptor` make handles that are not inheritable,
  and the one crate that passes handles to a child, `windows-spawn` (one
  0.1.0 release, August 2026), puts each handle in an argument of its own
  and cannot write both into one switch. So the port stays on every
  platform, still a [known limit](../guide/intuituive/embed.md), and
  rs-rich-embed's 0.0.19 change is its manifest only. The workstream is
  first in line for 0.0.20 once Windows has a way through.

### 6. Docs: an example and a picture on every page

Docs only: no package versions move for this workstream, and it starts at
once, beside the others.

- **The Python site gets its pictures.** Each Python page's examples move
  into `crates/rich-py/examples/docs/<page>.py`, rendered by a new
  `scripts/capture_python_docs.py` with `Console(record=True)` into
  `docs/python/media/*.svg`, and shown under each example. `--check` runs
  in the Python workflow, so a picture that no longer matches its code
  fails CI, as `capture_guide.py --check` does for Rust.
- **Every Rust guide page shows output.** A `guide_*.rs` example and its
  screenshot for each page the audit listed, the overviews included, and
  for each explorer the explorers page describes, captured by
  `scripts/capture_guide.py` like the rest. The two procedure pages are
  the exception.
- **Recordings of 0.0.18:** tapes for the stylesheet (with hot reload),
  table sorting, resizing and the cell cursor, the lazy tree, tooltips
  and drag-and-drop, accessible and linear mode, `rich serve` and the
  terminal pane; and for 0.0.19's own features as they land (alignment,
  the text area, the surface). Each is on the
  [recordings](../recordings.md) page and on its guide page.
- **The browser pages:** screenshots of the xterm.js page and the DOM
  renderer, taken with Playwright from a scripted session, on the
  [web](../guide/intuituive/web.md) page.
- **Runnable, not pasted:** every new example is a compiled example
  program or a script CI runs, so the code on a page cannot drift from the
  code that made its picture.

## Order of work

1. **Docs (6)** starts at once; it needs nothing else.
2. **Surface (4)** next among the code, because it moves intuiTUIve's
   screen and painter, which alignment and the text area draw through.
3. **Alignment (1)** and **the text area (2)** in parallel after it.
4. **Process isolation (3)** and **the DevTools pipe (5)** at any time;
   neither touches the others.
5. The tapes for 1, 2 and 4 join workstream 6 as each lands.
6. The release test: three independent audits, as for 0.0.18.

## Decisions

Decided on 2026-10-12 (5 on 2026-10-08):

1. **Stylesheet names:** CSS's (`align-items`, `justify-content`,
   `flex-wrap`, `align-self`, `align-content`), as the sheet is a CSS
   subset.
2. **Wrapping:** in this release, with alignment.
3. **The text area's editing model:** one buffer, `edit::Buffer` in
   rs-rich-interact, shared with `rich_interact::TextArea`, so grapheme
   and paste fixes land once.
4. **Process isolation by default** for `serve`, with threads as the
   opt-out.
5. **`Surface` in rs-rich-ext.** It bumps rs-rich-ext, so every crate that
   depends on it moves too (see [Package impact](#package-impact)).
6. **The DevTools pipe ships on every platform or none.** Windows does not
   keep the port while Linux and macOS move to the pipe; behaviour stays
   the same everywhere (see [workstream 5](#5-devtools-over-a-pipe-embed)).
7. **Browser screenshots** are regenerated at release time, not checked in
   CI, since browser font rendering differs between machines. The terminal
   recordings stay CI-checked.

## Not in this release

- An SSH front end for served apps (after process isolation).
- A visual stylesheet editor, sibling selectors, `!important`, animations
  or transitions in the stylesheet.
- Platform accessibility bridges (AT-SPI, UI Automation, the macOS API).
- Anything in core.
- Feature work from the theme milestones; 0.0.20 and 0.0.21 are the
  [parity releases](1.0.0.md#stage-2-parity-complete-and-the-marketplace-0020-to-0022).

## Review focus

- **Alignment against CSS:** every alignment and wrap case matches what a
  browser lays out for the same boxes; nothing changes for a container
  that sets none (`Stretch`, `Start`, no wrap).
- **The text area under load:** a 100,000-line file, a long line without
  wrapping, wide and combining characters, a paste with controls in it,
  undo across a paste.
- **Isolation for real:** a session that crashes, hangs or eats memory
  does not touch the others; no orphan process survives a closed tab, a
  server stop or a signal.
- **The `Surface` moves without a behaviour change** for intuiTUIve:
  every intuiTUIve test, tape and the benchmark gate pass unchanged.
- **No `unsafe` enters the workspace.** (The web view's port stays until
  the pipe lands in 0.0.20; see [workstream 5](#5-devtools-over-a-pipe-embed).)
- **Docs pictures match their code:** `capture_guide.py --check`,
  `capture_python_docs.py --check` and `rich record --check` all pass.
